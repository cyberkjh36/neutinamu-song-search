## WEB 2.7 · 마이크 상태가 잘 보이는 화면

- 큰 원형 마이크와 “눌러서 노래 제목을 말하세요” 안내를 추가했습니다.
- 대기: 마이크 꺼짐. 시작 요청/권한 대기: 노란색 “마이크 켜는 중”. 브라우저가 인식 시작을 알리면 녹색 “마이크 켜짐 · 듣고 있어요”와 부드러운 링 표시가 나타납니다.
- 브라우저가 소리를 감지하면 “소리가 들어오고 있어요”와 막대 표시가 나타납니다. 이 표시는 음량계가 아니며 소리 감지 이벤트가 없을 때 임의로 움직이지 않습니다. 기기마다 감지 이벤트 제공 여부가 다를 수 있습니다.
- 음성 입력 마무리 중, 입력 완료/마이크 꺼짐, 권한 오류도 구분합니다. 녹색 표시는 `start` 또는 `audiostart` 등 브라우저의 확인을 받은 뒤에만 표시합니다. 오류·완료 후 또는 종료 중에 늦은 이벤트가 와도 다시 켜짐으로 표시하지 않습니다.
- “말하기 완료”는 정지 아이콘으로, 취소는 별도 버튼으로 표시합니다. 모션 줄이기 설정도 따릅니다.
- 새 안내는 기존 11개 언어에 적용했습니다. 음성 결과를 확인하고 검색 버튼을 눌러 보내는 방식, 다음 곡 검색, 연결번호, PC 전달/예약 기능은 유지합니다. PC 프로그램 재설치는 필요 없습니다.

기존 QR로 열고 새로고침한 뒤 상단 **WEB 2.7**을 확인하세요.

검증: `node --test wk-tests/*.test.mjs` **66개 통과**. 별도 로컬 테스트 화면에서 실제 Chromium으로 11개 언어 × 3개 너비(320/390/430px) × 5개 상태(시작/듣기/소리 감지/마무리/오류), 총 **165개**의 상태 표시·문구·가로 넘침 검사를 통과했습니다. 실제 화면도 확인했습니다. 음성 서비스와 PC 응답은 테스트 대역이며, 실물 Android/iPhone 마이크 인식은 이 환경에서 직접 시험하지 않았습니다.

이벤트 기준: https://webaudio.github.io/web-speech-api/ (SpeechRecognition events).

WEB 2.5: WEB 2.4에서 추가한 음성인식 대기시간 처리의 오류를 수정했습니다. 브라우저의 `setTimeout`과 `clearTimeout`을 클래스 메서드처럼 호출하면서 `TypeError: Illegal invocation`이 발생했고, 실제 `recognition.start()`가 호출되기 전에 "이 브라우저에서 음성인식을 사용할 수 없습니다" 안내가 나왔습니다. 타이머를 전역 객체에 연결한 래퍼로 호출하도록 바로잡았습니다. WEB 2.5 검증: Node 검사 57개와 Chromium 브라우저 시나리오 12개를 통과했습니다. 수정 전 WEB 2.4가 Android/iPhone 형태의 화면 모두에서 시작하지 못하는 것을 재현한 뒤 수정본의 시작·결과·종료·재시도·12초 무응답 제한·완료 버튼 후 2.5초 종료 처리를 확인했습니다. 이번 브라우저 검사는 타이머를 모의 구현으로 바꾸지 않았습니다. 음성 서비스와 PC 전달 서버는 테스트 대역이므로, 실물 Android/iPhone 마이크의 인식 성공까지 검증한 것은 아닙니다. 앞선 WEB 2.4 검사에서 사용한 모의 시계는 브라우저 고유의 호출 규칙을 검사하지 않아 이 오류를 놓쳤습니다. 회귀 검사에서 모의 시계를 제거하고 전역 호출 규칙 검사도 추가했습니다.

WEB 2.4: iPhone/Safari에서 음성인식 창을 열거나 음성 서비스를 시작하지 못할 때 아무 반응 없이 중단되던 경로를 수정했습니다. 구형 브라우저의 대화상자 대체 표시, 시작 예외 처리, 12초 시작 응답 제한, 45초 세션 제한을 추가했습니다. 오류 시 안내·다시 말하기·키보드 마이크 입력 버튼을 11개 언어로 표시합니다. Safari가 최종 결과 없이 임시 결과만 반환해도 확인 가능한 검색어로 남기며 자동 전송하지 않습니다. 반복 결과가 같은 검색어에 중복으로 붙지 않도록 했습니다. 기존 PC 연결·언어 선택·다음 곡 검색 동작은 유지합니다. 기존 QR 주소는 유지됩니다. PC 런처 재설치는 필요 없습니다.

iPhone에서 말하기가 안 되면 Safari로 열고 마이크/음성인식 허용 요청을 확인하세요. **키보드 마이크로 입력**을 누르면 입력칸이 선택됩니다. 휴대폰 키보드의 마이크를 직접 누르고 말한 뒤 **PC에서 검색**을 누르세요. 키보드에 마이크가 없다면 설정 → 일반 → 키보드 → 받아쓰기 활성화를 확인하세요. 웹페이지가 iOS 권한이나 받아쓰기를 대신 켤 수는 없습니다.

WEB 2.4 당시 검사 기록(모의 시계 사용): Node 자동 검사 56개와 Chromium 실제 화면/클릭 검사 9개(음성 서비스·PC 전달 서버는 모의 구현)를 통과했습니다. 구형 dialog API 부재, 무응답, 권한/생성자/시작 실패, 재시도, 키보드 전환, 11개 언어, 명시적 검색 전송과 다음 검색 초기화를 확인했습니다. 실제 iPhone 11/18 및 Android 마이크는 직접 검증하지 않았으며, Linux WebKit 검사는 실행 환경 의존성이 없어 완료하지 못했습니다. 특정 기기의 무응답 원인을 OS 버전만으로 확정한 것은 아닙니다.

호환성 참고: [Safari 14.1 음성인식](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/), [Safari 15.4 dialog 지원](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/), [Apple iPhone 받아쓰기](https://support.apple.com/guide/iphone/dictate-text-iph2c0651d2/ios).

WEB 2.3: PC에서 검색 완료를 확인하면 검색 버튼이 **다음 곡 검색**으로 바뀝니다. 누르면 이전 검색어를 지우고 입력칸을 선택하며 PC 연결과 선택 언어는 유지합니다. 새 곡명을 입력하거나 말한 다음 **PC에서 검색**을 눌러야 전송됩니다. 직접 글자를 고치거나 새 음성이 인식되면 즉시 새 검색으로 전환합니다. 검색 실패 시에는 입력을 보존하여 재시도할 수 있습니다. 11개 언어에 적용했으며 PC 런처는 다시 받을 필요가 없습니다.

Android Chrome과 iPhone Safari에서 여는 웹 프로그램입니다. APK 설치나 Bluetooth 페어링은 필요 없습니다. PC 런처 **1.3.52 이상**과 PC·휴대폰의 인터넷 연결이 필요합니다.

1. PC에서 새 런처의 START.exe 실행 → 국기 선택 → 휴대폰 아이콘.
2. 휴대폰 카메라로 PC의 QR을 찍거나 위 주소를 열고 PC에 표시된 8자리 번호 입력.
3. 국기/언어 선택 → PC 연결 → 노래 제목 말하기.
4. 인식된 글자를 확인하고 **PC에서 검색** 누르기.
5. PC 검색 결과의 **＋ 예약**으로 곡을 추가합니다.

휴대폰 3대까지 연결됩니다. PC 검색 화면은 함께 사용하므로 마지막 검색이 표시됩니다. 앞선 검색은 PC 연결창의 최근 검색에서 다시 열 수 있습니다. PC 연결창을 닫거나 새 번호를 만들면 다시 연결해야 합니다. 연결번호는 최대 24시간 유지됩니다. 휴대폰 화면을 잠그거나 브라우저를 오래 뒤로 보내면 연결이 끊길 수 있습니다.

11개 언어: 한국어, ไทย, Filipino, Tiếng Việt, नेपाली, Монгол, Bahasa Indonesia, ລາວ, မြန်မာ, 中文, 日本語. 해당 언어로 UI를 표시하고 음성인식 언어를 지정합니다. 실제 음성인식 지원은 기기·브라우저·음성 서비스에 따라 다릅니다. 말하기가 작동하지 않으면 입력칸을 누른 뒤 휴대폰 키보드의 마이크를 사용하거나 직접 입력하세요. 말하기 버튼은 인식 결과만 입력하며 자동 검색하지 않습니다.

마이크 허용 요청은 말하기를 누를 때 발생합니다. 음성은 브라우저/운영체제의 음성 서비스에서 처리될 수 있습니다. 이 앱과 전달 서버는 녹음 파일을 받거나 저장하지 않습니다. 확인한 검색어와 언어만 HTTPS 서버를 통해 PC로 전달됩니다. 검색어는 PC의 처리 확인 후 서버에서 지워지며, PC 연결창의 최근 검색 목록은 창을 닫을 때 사라집니다.

GitHub Pages는 화면을 제공하고, 별도 HTTPS 서버가 검색어를 전달합니다. 서버 주소는 relay-client.mjs의 ENDPOINT에 있습니다. 번호를 아는 사람이 PC 검색을 요청할 수 있으므로 번호는 이용할 손님에게만 알려 주세요.

기존 저장소의 노래번호 검색 화면은 루트 주소에 유지합니다. /wk/는 별도 캐시 범위를 사용합니다.

검증: Node UI 이벤트/번역 검사, HTTPS 전달/인증/3대 제한/중복 방지 검사 및 PC 클라이언트 검사. 실제 Android·iPhone 마이크와 Windows UI 실기 검증은 별도로 필요합니다.

WEB 2.1: 브라우저 fetch의 호출 대상을 고정해 PC 연결 전 통신 오류를 수정했습니다. 연결 진행/실패는 PC 연결 버튼 아래에 표시합니다. 10초 응답 제한과 재시도를 지원합니다. PC 1.3.54는 QR 위 설명 높이를 자동 조절하고 새 웹 버전 주소를 QR에 넣습니다.

WEB 2.2: Android의 삼성 인터넷 등에서는 화면 맨 위에 **Google Chrome으로 열기** 버튼을 표시합니다. 버튼을 직접 누르면 Android Intent로 Chrome을 지정하여 같은 화면을 엽니다. 연결번호·선택 언어·입력한 곡명은 주소의 fragment로 전달되어 GitHub 요청에 포함되지 않습니다. 기존 연결은 해제하고 Chrome에서 PC 연결을 다시 누릅니다. 기존 8자리 QR은 그대로 사용할 수 있으며 PC 1.3.54를 다시 받을 필요가 없습니다.

Chrome과 iPhone Safari에서는 전환 안내를 숨깁니다. Chrome 실행을 확인하지 않고 성공했다고 표시하거나 자동으로 반복 실행하지 않습니다. Chrome이 없거나 브라우저가 실행을 막으면 설치/확인 링크와 기본 브라우저 안내를 사용하세요. QR을 처음 여는 앱은 휴대폰 설정 또는 QR 스캐너가 결정하며 웹페이지가 그 기본값을 바꿀 수는 없습니다. 삼성 휴대폰: 설정 → 애플리케이션 → 기본 앱 선택 → 브라우저 앱 → Chrome. 메뉴 이름은 기기 버전에 따라 다를 수 있습니다.

## WEB 2.6 - iPhone에서 Safari로 열기

기존 PC QR을 iPhone/iPad에서 열면 큰 **Safari로 열기** 버튼을 표시합니다. 버튼을 직접 누르면 `x-safari-https:` 링크로 같은 웹앱을 Safari에 열도록 요청합니다. 연결번호, 선택 언어, 입력한 곡명은 fragment로 전달하며 새 화면에서도 **PC 연결**과 검색 버튼은 사용자가 누릅니다. 연결주소 복사와 전체 선택 안내도 11개 언어로 제공합니다. PC 설치파일이나 QR 주소를 바꿀 필요는 없습니다.

QR을 처음 여는 앱이나 기본 브라우저 설정은 웹사이트에서 바꿀 수 없습니다. 이 Safari URL scheme은 모든 iOS/스캐너에서 작동한다고 보장할 수 없으며 앱 열기 확인창이 표시될 수 있습니다. 자동 전환이나 재시도 루프는 만들지 않습니다. Safari와 내장 Safari 화면은 UA만으로 확실히 구별할 수 없어 Apple 모바일에서 공통 안내를 표시하고, 이미 Safari인 손님은 **이 화면에서 계속하기**를 누를 수 있습니다. 전환 URL로 다시 들어오면 안내만 접고, Safari 실행 성공이나 마이크 허용을 추정하지 않습니다.

전환이 막혀도 기존 연결을 바로 끊지 않습니다. 전환 요청 후 실제로 페이지가 숨겨지거나 닫히면 기존 PC 연결을 해제합니다. 복사 실패 시 연결주소 전체를 선택해 수동으로 복사할 수 있습니다. 말하기/연결/전송 중에는 전환 버튼을 사용할 수 없습니다. Android Chrome 전환, 음성인식, 검색 동작은 기존대로 유지됩니다.

검증: `node --test wk-tests/*.test.mjs` 61개 통과. 실제 Chromium에서 Safari 안내/주소 전달/복사 거부/11개 언어/320px 화면/연결 해제/다음 곡 검색 7개 시나리오 통과. `wk-tests/voice-browser.mjs`의 기존 마이크 UI 및 native timer 회귀 9개 시나리오도 통과했습니다. 브라우저 검사는 음성과 PC 통신을 대체한 환경이며 실제 iPhone의 Safari 앱 전환과 마이크는 실기 확인이 필요합니다. WebKit 실행은 이 환경의 시스템 라이브러리 부족으로 지원되지 않습니다.

참고: [Safari URL scheme의 앱별 동작 차이](https://bugzilla.mozilla.org/show_bug.cgi?id=1986355), [Apple 기본 앱 설정](https://support.apple.com/ko-kr/121430).
